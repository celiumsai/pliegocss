# PliegoRS development reload loop

Status: source-pinned local two-process/SSE gate green; controlled Chromium replay observed

PliegoCSS does not need its own HTTP or WebSocket server. The current PliegoRS development server
already owns browser reload through its loopback-only `pliego dev` server and `/_pliego/reload` SSE
endpoint. PliegoCSS only needs to publish the stylesheet as a project source asset.

Run both processes from the application project:

```console
# Terminal 1
pliego-cssc watch \
  --source src \
  --config pliego.theme.toml \
  --theme \
  --format pretty \
  --output assets/pliego.css \
  --manifest assets/pliego.manifest.json

# Terminal 2
pliego dev
```

The intended development flow is:

```text
Rust/theme edit
→ pliego-cssc validates and publishes changed asset bytes
→ pliego dev observes the project asset and rebuilds
→ a successful PliegoRS build advances its reload generation
→ the browser's existing EventSource triggers a full-page reload
```

The cross-repository gate pins the PliegoRS CLI source, runs both processes with Rust 1.86, and
verifies 20 alternating `pc!` edits plus invalid and unchanged-output negative cases. Run it with:

```console
pnpm integration:pliegors-dev
```

On native Linux x64, changed CSS reached disk at 228.3 ms p50 / 230.4 ms p95.
Matching HTML/CSS and exactly one stable SSE generation converged at 1.696 s
p50 / 1.697 s p95. These are server/site convergence measurements. A controlled local Chromium
replay separately observed `p-4`/16 px become `p-6`/24 px in the same tab without manual navigation.
See the [development-loop evidence](../benchmarks/pliegors-dev-loop.md).

`watch` compares the exact generated bytes with each existing destination. Identical CSS is not
replaced, so its modification time does not cause a redundant PliegoRS rebuild. If only provenance
changes, the manifest may be replaced while the CSS asset remains untouched. The negative gate uses
an external-input no-op for which both CSS and manifest remain exact, including modification times.
Invalid PliegoCSS input keeps the complete last valid publication group.
PliegoRS exposes its bounded build diagnostic at HTTP 500 for that failed
generation, then recovers through the same SSE channel after valid source is
restored.

The adjacent `.pliego.lock`, `.tmp`, and `.bak` files are a reserved publication-coordination
namespace, not application assets. The pinned PliegoRS watcher ignores them so a held advisory lock
cannot trigger a scan failure or rebuild; it still observes every changed final CSS/manifest file.
`pliego dev` filters access-only notifications before they can starve real
filesystem changes and does not publish another generation for a no-op build
with no changed artifacts. This coalesces a Rust edit and its generated assets
into one successful SSE generation.

Native Windows/Linux filesystem events schedule source captures; exact snapshots are confirmed across two
captures separated by up to 100 ms before compilation. A 2 s fallback capture covers missed events,
and backend setup failure retains 100 ms polling. Unchanged Rust files reuse both their syntax scan
and theme-scoped semantic IR; changing the theme retains scans and invalidates all semantic entries.

## Asset ownership

Write `pliego.css` under a source asset directory such as `assets/`, not inside the generated site
output directory. PliegoRS excludes its output, `target`, `node_modules`, and VCS metadata from the
development watcher; generated output may also be replaced by the next build.

The intended SSG seam is a normal PliegoRS asset plus stylesheet link:

```rust
const PLIEGO_CSS: &[u8] = include_bytes!("../assets/pliego.css");

let site = Site::new().asset(Asset::new(
    "assets/pliego.css",
    PLIEGO_CSS.to_vec(),
));
let head = Head::new("My page").stylesheet("/assets/pliego.css");
```

The cross-repository integration gate now executes this API with compiler-produced global and route
CSS bundles, verifies the emitted `<link>` elements, and cross-checks the deployed asset hashes.
Those assets are generated together from a versioned
[declarative bundle plan](../reference/bundle-plan.md). The current application-owned adapter derives
the supported [reachability sidecar](../reference/reachability-schema.md) and automatic source
partitions from one validated PliegoRS product registry. It is exercised by the integration fixture,
but is not yet packaged as a one-command starter feature. `pliego-cssc bundle` remains a one-shot
command rather than a multi-bundle watch loop.

## Security and limits

- Keep the default loopback binding for `pliego dev`; LAN exposure must remain explicit.
- PliegoCSS does not execute an `--on-success` shell command and opens no network listener.
- This is full-page browser reload, not CSS-only HMR.
- The automated gate fails if one accepted edit produces a transient stale CSS/HTML pair, a second
  reload generation, or a served stylesheet whose SHA-256 differs from the compiler artifact.
- Production builds and preview output must not contain the development reload client.

The local F6 browser seam is now closed by the executable fixture and controlled Chromium replay.
Hosted multi-browser execution remains a release gate. CSS-only HMR is also not implemented: a
successful PliegoRS build still performs a full-page reload.
